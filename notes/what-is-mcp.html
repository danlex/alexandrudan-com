What is MCP?

MCP, the Model Context Protocol, is an open standard for connecting AI applications to external tools and data. It gives a model a consistent way to reach systems it would otherwise only hear about secondhand, such as a database, a ticketing system, or a file store, and to act on them. The official analogy is a USB-C port for AI: one standard plug instead of a custom integration for every tool.

The note

MCP uses a simple client-server shape. The host is the AI application you are using, such as Claude Desktop or Claude Code. For each external system it wants to reach, the host starts one client, and each client holds a dedicated connection to one server. A server is just a program that exposes capability over the protocol; it can run locally on your machine or remotely on a vendor's platform. What a server offers comes in three kinds: tools (actions the model can call, like "create ticket" or "run query"), resources (data it can read, like a file or a record), and prompts (ready-made templates). The model discovers what is available, then calls it, the same way regardless of what the tool actually does (modelcontextprotocol.io).

A hypothetical logistics company wants its support assistant to answer "where is my shipment?" Without MCP, someone copies tracking data into the chat by hand. With an MCP server wrapping the carrier's tracking API, the assistant calls a tracking tool directly, reads the result, and replies, inside whatever limits the server allows. The company builds the server once, and any MCP-capable client can use it.

Two points are easy to get wrong, and both are about trust. A connection is not access. MCP defines how a client and server talk, but authorization is handled separately: remote servers typically use OAuth or API tokens, and the standard is explicit that a server must reject tokens that were not issued for it and must verify every request rather than trust that a caller is connected (MCP security guidance). Tools also take real actions, so the usual risks apply. A server can return content that tries to steer the model into misusing a tool, the tool-use version of prompt injection, and an over-broad set of permissions widens the blast radius if anything goes wrong, which is why the standard guidance is to require user consent before running a local server, grant the least privilege that works, and treat each server as untrusted until you have reason not to.

MCP earns its place when you keep pasting the same external data into a chat, or when an assistant needs to act in a system rather than just talk about it. It is now supported across a range of clients and servers, including Claude, ChatGPT, and editors like VS Code and Cursor, so a server you build is reusable well beyond one app. Where it fits in a larger system is one layer of how AI agents reach production, and it pairs with the discipline of evaluating what those agents do. For a plainer starting point, see what an AI agent is.

In one line

  • Host: the AI application (e.g. Claude Code).
  • Client: one connection, managed by the host, to one server.
  • Server: exposes tools, resources, and prompts; runs locally or remotely.

FAQ

Common questions.

Is MCP only for Claude?

No. MCP is an open standard, not an Anthropic-only feature. It is supported across many AI applications and tools, including Claude, ChatGPT, and editors like VS Code and Cursor, so a server you build once can be used by any MCP-capable client.

Does connecting an MCP server give it access to everything?

No. The connection and the authorization are separate. Remote servers typically use OAuth or API tokens, a server must reject tokens that were not issued for it, and the guidance is to require user consent and grant the least privilege that works. Treat a new server as untrusted until you have vetted it.
